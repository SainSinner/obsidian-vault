## Контекст задачи

Проектирую слои данных и разграничение доступа в **Trino** для домена **HR**.
Архитектура уже согласована в предыдущей сессии — не предлагай альтернативы
без запроса, помогай развивать принятое решение.

### Окружение

- Trino от DevOps (дистрибутив не выбираю), плагины **Ranger и OPA доступны**
- **Apache Ranger уже есть в компании** (UserSync из AD) — выбран как механизм авторизации
- Аутентификация: **LDAP/AD** (люди + сервисные УЗ, всё через AD)
- Источники: **S3 + Iceberg** (lakehouse), реляционные БД, Kafka
- Потребители: аналитики (SQL/Jupyter), ETL-джобы, BI, приложения по API
- Аудит: желателен → Ranger audit (log4j на старте)

### Принятые решения

**Слои и нейминг** (каталог `lake`, слои = схемы):
- `lnd_<src>_t` / `lnd_<src>_v` — приземление по источнику
- `raw_<src>_t` / `raw_<src>_v` — RAW по источнику
- `l1_t` / `l1_v` — интегрированный слой (деление t/v есть)
- `l2` — витрины (без деления t/v)
- `meta` — реестры (в т.ч. `source_systems`)
- `<src>` = 4-значный id системы из корпоративной **CMDB**; доменный префикс НЕ используется
- Суффиксы: `_t` = таблицы, `_v` = представления
- В L1/L2 — техническая колонка `source_system_id`
- Каталоги источников (`pg_*`, `kafka`) закрыты для аналитиков

**Группы AD:** `svc-etl-hr` (сервисная), `hr-data-engineers`, `hr-de-sensitive`
(допуск к чувствительным источникам), `hr-analysts-privileged`, `hr-analysts`,
`bi-readers`, `svc-bi`, `svc-api-*`, `trino-admins`

**Матрица доступа (кратко):**
- svc-etl-hr: RW везде
- hr-data-engineers: R на lnd_*, RW на raw_*/l1/l2, DENY на чувствительные raw
- hr-de-sensitive: то же + RW на чувствительные raw
- hr-analysts-privileged: R на raw_*/l1_t/l1_v/l2 (DENY на чувствительные raw)
- hr-analysts: только l1_v + l2
- bi-readers/svc-bi/svc-api: только l2

**Защита чувствительных данных (ПДн, зарплаты) — 3 рубежа:**
1. Аналитики не имеют доступа к LND/RAW вообще
2. Чувствительные источники в RAW: точечная **deny-политика Ranger** на
   `raw_<sens>_*` (deny приоритетнее wildcard-allow); доступ только
   svc-etl-hr + hr-de-sensitive
3. L1: аналитики через `l1_v` (view с security definer), маски через
   `CASE WHEN contains(current_groups, 'hr-analysts-privileged') ...`;
   Ranger-маски на l1_t — второй контур

**Прочее:**
- Политики Ranger на wildcard `raw_*`/`lnd_*` → новые источники подхватываются автоматически
- Row-level: пока не реализуем (признак не определён); точки расширения:
  Ranger row-filter (простое условие) или secured view по current_user (сложное)
- BI: старт с svc-bi, impersonation — позже (BI-система не выбрана)
- Онбординг источника: id из CMDB → реестр → схемы → (deny если чувствительный) → джобы
